# UI localization

Status: MVP contract under D021; application implementation has not started. Ukrainian as default, English as secondary, catalog-based UI copy, and a profile language switcher are user requirements. Persistence and formatting details below are implementation defaults.

## Languages and scope

| Language | Stored UI code | Selector label | Role |
| --- | --- | --- | --- |
| Ukrainian | `uk` | Українська | Default for new accounts and an unconfigured browser |
| English | `en` | English | Secondary, selected in the profile |

Use `uk` for Ukrainian, not the country code `ua`. Both catalogs ship with the frontend; language selection needs no external service or translation API.

All application-authored user-facing text must come from stable i18n keys. This includes navigation, page titles, buttons, form labels/placeholders, tooltips, accessible names, dialogs, validation/errors, notifications, loading/empty states, storage units/messages, field-review controls, save states, and version-history/retention text. Apply this across login, library, profile, and workspace, including settings and embedded-editor controls exposed by the app. The English wording in planning documents describes behavior; it is not permission to hardcode English in components.

Use supported localization hooks or project-owned localized controls for editor UI. E00 must verify that the chosen free integration can satisfy both languages; vendor menus/dialogs do not receive an automatic exemption. Browser/OS-controlled dialogs are outside the application's translation catalogs.

## Profile preference

- Store a validated `ui_language` on the user with supported values `uk` and `en`, defaulting to `uk`. Existing accounts receive the Ukrainian default when the preference is introduced.
- The profile contains a language selector showing both native names. A successful save applies the language throughout the app without a full-page reload or resetting active form/editor state. Announce success in the selected language.
- Persist the preference on the server; use it after refresh, logout/login, and login from another browser. The authenticated account preference takes precedence over any browser-local preference.
- Before authentication, default to Ukrainian. A browser may remember the last successfully selected language for the login page. Browser language detection must not override the Ukrainian default or a saved account preference.
- Reject unsupported language values in the profile API. If saving fails, retain the previous saved language and show a localized recoverable error; do not present a failed update as persistent.
- A locale update must not require navigation away from unsaved work or recreate the editor. Changing language creates no document revision, save/export job, or quota charge. Normal navigation to the profile still follows the existing unsaved-work safeguards.

## Catalogs, API data, and formatting

- E01 establishes both catalogs and the common translation/formatting entry point before product pages are implemented. Choose and pin a free React-compatible i18n library there; this contract does not select a package or version.
- Use semantic keys grouped by feature. Add/update Ukrainian and English messages in the same feature PR, including interpolation and the plural forms required by each language. Translate complete messages instead of concatenating fragments.
- API errors and job/review states use stable machine-readable codes and typed parameters. The frontend maps them to catalog keys, including validation-field names. Unknown/unavailable responses show a localized generic error; raw FastAPI/Pydantic or third-party English messages are not product UI.
- Format interface dates, times, numbers, counts, and storage amounts with locale-aware formatters (`uk-UA` for Ukrainian and `en` for English). Language changes do not change timezone policy, canonical API values, or document field values. Update the page's HTML `lang` attribute and localized title/accessibility text.
- Use Ukrainian as the runtime fallback for a missing or invalid client locale. A missing message may fall back to Ukrainian at runtime to keep the UI usable, but missing translations must fail development checks/CI rather than quietly shipping an incomplete English catalog.
- Escape interpolated user data. Do not interpret translations or document values as executable markup.

## Document content remains original

The interface locale is separate from the language of an uploaded DOCX. Document text, titles/filenames, extracted or user-renamed field labels, field values, and retained revisions remain user data in their original language. Never use these values as translation keys, automatically translate/transliterate them, or change DOCX language/proofing metadata when switching the UI.

Generic application labels such as “Unnamed field,” type names, and review statuses use i18n keys. A generic display fallback must not overwrite the underlying field's label with whichever translation is currently visible. Show user-authored text as data with appropriate escaping.

The [Version badge](VERSION_BADGE.md) has a narrow user-specified display rule under D022: retain visible `version:` and `development` in both catalogs, with a localized accessible label. Store these messages in i18n and interpolate the commit as data; this does not exempt other application copy from translation.

## Required acceptance evidence

- Catalog checks cover matching logical message keys, nonempty translations, matching interpolation parameters, and valid locale-specific plural forms. Missing/invalid translations and prohibited hardcoded application copy fail required CI under [CI and deployment](CI_CD.md).
- Browser acceptance covers all four pages and history/settings/sidebar states in both languages, with Ukrainian as the initial default. Check accessible names, errors, storage formatting, and long Ukrainian text without clipping essential controls.
- Profile tests cover successful switching, save failure, invalid API values, persistence after refresh and a new login/browser session, and account preference winning over stale browser state.
- A language change preserves active drafts, document field labels/values, and selection/undo state. Verify that it neither creates a revision nor changes original or saved DOCX bytes. Localization is not an export operation.
- Keep the independent backend/frontend 90% line and branch gates. Catalog validation supplements behavioral tests; it is not a substitute for coverage or an implemented CI gate at this planning stage.
